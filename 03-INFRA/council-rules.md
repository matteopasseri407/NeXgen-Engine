# Council rules for agents

**Council exception (documented, deliberate).** The Agent Council (`council/`) is the one documented, deliberate exception to firecrawl-first: every seat prompt (`council/prompts/*.md`) tells the consulted model "non hai strumenti e non devi usarne" — no tool of any kind, firecrawl included. Seats run headless/sandboxed by design (see the per-CLI sandbox flags and the "consulenti senza mani" rationale in `council/council.py`): a non-interactive seat has no way to satisfy a tool-confirmation prompt anyway. This rule governs your own normal operation, not what a Council seat prompt permits.

**Council CLI-level enforcement is asymmetric — do not assume parity across seats.** The textual "no tools" line above is present in every seat prompt regardless of CLI, but whether the *CLI itself* also makes tool calls impossible (so an ignored prompt still can't succeed) differs per vendor, and this was verified live against the installed binaries rather than assumed: `claude` (`--tools ""`) is comprehensively CLI-blocked — no tool exists to call. `ollama` has no tool-calling surface at all unless the undocumented `--experimental` flag is passed, which the Council never does — verified safe by construction. `codex` (`-s read-only`) and `agy` (`--sandbox`) are both documented, by the vendor's own help text/product docs, as scoping the shell/terminal-command tool only, not MCP servers — no CLI flag exists in their current shipped release that closes that gap without risking a broken seat, so they rely on the prompt text alone, same as `opencode`, which has no CLI-level block whatsoever. Full per-CLI findings and what was actually tested: `council/council.py`, comment above `_build_seat_command`.

**Council seats answer from the turn's context only.** A seat's own native cross-session memory (see "Native memory is never authoritative" in the bootstrap) is exactly the kind of un-shared, un-reviewed private context the whole point of Council is to route around — a seat that quietly draws on it instead of the prompt/context it was actually given defeats the "genuinely different, independently-reasoning vendor" premise. Answer only from what this turn's prompt provides.

## Agent Council trigger: full rule (moved from the bootstrap)

**Agent Council trigger — only if configured.** This applies only when the user already has Council configured on this machine (a `seats.yaml` is present); if it isn't, don't suggest setting it up mid-task — that's a separate, explicit choice for the user, never something to volunteer as a side effect of this trigger. When it is configured: Council exists to challenge your reasoning across genuinely different models and vendors — different training, different blind spots, different failure modes — not to parallelize the same kind of thinking faster. Never propose it as "let's get this done quicker"; propose it when a differently-biased mind could catch something you can't see from inside your own reasoning. For long, difficult, sensitive tasks, extensive codebase reviews, irreversible architecture decisions, or when you're about to contradict an earlier conclusion in the same session: run `council propose` (no role = full table) and show the user primary + fallback per role, the rationale, and what's actually available on this machine. Prefer `challenge` over `brainstorm` when the goal is to stress-test a conclusion, not just add more voices. Never call `--seat`/`--sequence` yourself — only the user picks and authorizes. This applies to subagents too: a subagent that hits this trigger surfaces the proposal to the orchestrating session/user, it never invokes Council on its own. Propose once per task; if declined, don't re-propose on the same task.
